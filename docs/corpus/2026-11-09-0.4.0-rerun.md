# Corpus re-run with the released 0.4.0 CLI (2026-11-09)

The [2026-11-03 corpus report](2026-11-corpus-report.md) ran a development build (its JSON reports say
`"version" : "0.1.0-SNAPSHOT"`). Launch content must cite numbers produced by the version people install, so the
same corpus was run again with the **released 0.4.0 CLI**.

**Result: no change.** 199 findings at the same commits, finding by finding: same rule, severity, module, subject,
file, line and column, and the same message, why and fix text. Same 282 modules, same 148 *not evaluated*
diagnostics, exit code 0 for all 20 repositories. The 1 false positive from the original review is still there,
unchanged. Every number in the original report's results section holds for 0.4.0.

Pinning to the old commits is deliberate: it isolates the CLI change from upstream changes. It also means these
numbers describe the projects **as of the 2026-11-03 commits, not today's HEAD**. A HEAD run is a new measurement
whose new findings would need a new review; it was not done.

### Reproduce

```bash
# verify the jar first (gh release download, or the asset URLs once the repository is public)
sha256sum -c --ignore-missing SHA256SUMS
SPRINGTUNE_JAR=$PWD/springtune-cli-0.4.0.jar \
CORPUS_PINS=docs/corpus/results/2026-11-03/shas.tsv \
  scripts/corpus/run-corpus.sh /tmp/corpus docs/corpus/results/2026-11-09-0.4.0
python3 -I scripts/corpus/summarize.py docs/corpus/results/2026-11-09-0.4.0
python3 -I scripts/corpus/diff-runs.py docs/corpus/results/2026-11-03 docs/corpus/results/2026-11-09-0.4.0
```

`SPRINGTUNE_JAR` and `CORPUS_PINS` are new, optional inputs of `run-corpus.sh` (default behavior unchanged);
`diff-runs.py` is new and exits 1 when the finding sets differ.

**Correction to the case study and README wording.** Both say that 45 of 45 evaluable HikariCP services "wait up
to 30 s". The precise statement is: **all 45 evaluable HikariCP modules wait longer than the rule's 5 s threshold;
44 wait up to 30 s (38 on the unset default, 6 with `30000` written explicitly) and 1 waits 10 s**
(`jeecg-cloud-xxljob` in JeecgBoot). Leak detection is off in all 45. Of the 63 modules where HikariCP was
detected, the other 18 were *not evaluated* (11 build the pool in code, 7 load config from outside the
repository). 25 of the 45 are in the two tutorial collections (`ityouknow` 14, `xkcoding` 11). Launch content uses
the precise wording; fixing the case study and README is left to their owners.

## What was reviewed, and what was not

Honest scope of the review for this re-run:

- **No false-positive status changed, because no finding changed.** The rule for the launch was: any finding that
  appears, disappears or changes needs a manual review. The diff found none, so there was nothing new to classify.
- **The 199 findings were not re-reviewed by hand.** Their classification (198 correct, 1 false positive) is the
  author's 2026-11-03 review, carried over because the findings are identical. Cite the rate as
  **"1 of 199, reviewed by the author on the 2026-11-03 run; unchanged with 0.4.0"**.
- **Spot checks** done by hand on the 0.4.0 output:
  - `apache/dolphinscheduler`, module `dolphinscheduler-api`: the human-readable text output matches the excerpt
    quoted in the [case study](../case-study/what-we-found-in-20-spring-boot-projects.md#1-the-30-second-wait-nobody-chose)
    line for line (ST-HIKARI-001, ST-HIKARI-002, ST-TX-001, two *not evaluated* lines), plus the `Docs:` links the
    case study omits.
  - `spring-petclinic/spring-petclinic-microservices`: ST-HTTP-001 at `ApiGatewayApplication.java:55:16` and
    `AIDataProvider.java:37:27`, as in the case study.
  - `xkcoding/spring-boot-demo`, module `demo-codegen`: the known false positive (ST-TX-001; the module opens
    ad-hoc JDBC connections, no Spring-managed datasource) is still reported. It is still a false positive.

## Side observations (not corpus results)

- The 0.4.0 text and Markdown output link every rule to
  `https://github.com/pvgiang/spring-tune/blob/main/docs/rules/<rule>.md`. While the repository is private those
  links return 404 for everyone else; see the [launch checklist](../launch/checklist.md).
- The JVM in this sandbox prints `Picked up JAVA_TOOL_OPTIONS` to stderr; `run-corpus.sh` now deletes empty
  `.err` files only, so these were removed by hand. They are environment noise, not CLI output.
