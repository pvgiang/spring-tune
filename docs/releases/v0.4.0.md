SpringTune 0.4.0 is the **first release on Maven Central** and on the Gradle Plugin Portal. It proves guarded apply
mode against a real PostgreSQL, adds a server-side budget check, and publishes overhead numbers.

> **Correction (added after the release):** these notes say the Gradle plugin is on the Gradle Plugin Portal. It is
> **not listed there yet**: the Plugin Portal workflow had not been run when 0.4.0 shipped, and the Portal reviews a
> plugin's first version by hand. `plugins { id("io.github.winkytek.springtune") version "0.4.0" }` works anyway,
> because the Portal serves artifacts from Maven Central, where the plugin and its marker are published. This is
> proved by [post-release-smoke run 42563268215](https://github.com/pvgiang/spring-tune/actions/runs/42563268215):
> all 5 jobs green, including Gradle 8.14.3 and 9.8.2 resolving the plugin by id through `gradlePluginPortal()`
> only and through `mavenCentral()` only. If your build doesn't use `gradlePluginPortal()`, add `mavenCentral()` to
> `pluginManagement.repositories`. The Portal listing follows; nothing else about 0.4.0 changes.

## Install

Everything is on Maven Central under groupId `io.github.winkytek.springtune` (0.3.0 was a GitHub Release only,
see its [correction](https://github.com/pvgiang/spring-tune/blob/main/docs/releases/v0.3.0.md)). No extra repository is needed.

```xml
<dependency>
    <groupId>io.github.winkytek.springtune</groupId>
    <artifactId>springtune-spring-boot-starter</artifactId>
    <version>0.4.0</version>
</dependency>
<!-- optional, opt-in: adaptive concurrency limiter -->
<dependency>
    <groupId>io.github.winkytek.springtune</groupId>
    <artifactId>springtune-limiter</artifactId>
    <version>0.4.0</version>
</dependency>
<!-- CI check -->
<plugin>
    <groupId>io.github.winkytek.springtune</groupId>
    <artifactId>springtune-maven-plugin</artifactId>
    <version>0.4.0</version>
    <executions><execution><goals><goal>check</goal></goals></execution></executions>
</plugin>
```

```kotlin
// build.gradle.kts (Gradle 8.5+): from the Gradle Plugin Portal, nothing else to configure
plugins {
    id("io.github.winkytek.springtune") version "0.4.0"
}
repositories { mavenCentral() }   // the plugin resolves springtune-check-engine from here
```

Without the Portal, `pluginManagement { repositories { mavenCentral() } }` in `settings.gradle.kts` resolves the
same plugin from Central. The CLI is `springtune-check-cli-0.4.0-all.jar` on Central and on the GitHub Release.

## Everything from 0.3.0

0.3.0 was never on Central, so 0.4.0 is the first Central release of everything in it: the Gradle plugin, apply
plans, `springtune.mode=apply` (experimental), the adaptive limiter, the issue forms and Grafana dashboard. See the
[0.3.0 notes](https://github.com/pvgiang/spring-tune/blob/main/docs/releases/v0.3.0.md), including the coordinate change from `io.github.winky.springtune` (0.1.0).

## What's new in 0.4.0

### Apply mode, proven on a real PostgreSQL

Iteration 3's skeptic set a bar for leaving "experimental"; it is now recorded in the
[iteration-4 brief §2](https://github.com/pvgiang/spring-tune/blob/main/docs/delivery/iteration-4-brief.md#2-pre-registered-bar-for-leaving-experimental-posre-recorded-before-any-load-test-code).
Bars 2–6 are proven here; bar 1 (a design partner running advise in production) cannot be met yet, so **apply
remains experimental in 0.4.0**.

- **Load suite on real PostgreSQL** (Testcontainers `postgres:17-alpine` in CI, or an external server with
  `-Dspringtune.it.postgres.url`). Assertions only on what the database enforces: counts, verdicts, refusal codes,
  SQLSTATEs, server log lines and `pg_stat_activity`; never on latency or means.
  Module `springtune-loadtests` (never published): `PostgresApplyLoadTest`, `BudgetLoadTest`,
  `DatabaseGuardLoadTest`, 12 scenarios; 12/12 green in CI (Testcontainers) and in 6 local passes, every one with
  its product mutation shown to fail it ([docs/loadtests.md](https://github.com/pvgiang/spring-tune/blob/main/docs/loadtests.md)).
  - Three replicas raising at once never exceed the budget (bar 2), also with a surge 4th replica, another
    service holding connections, a short `maxLifetime`, and one replica reverting while the others raise.
    Server-side peak 15 for 3 replicas at cap 5 (usable budget 16, roles limited to 20); with another service holding
    3 connections, 19–20 client backends and zero SQLSTATE 53300.
  - `max-replicas` that excludes the surge pod reproduces the breach (SQLSTATE 53300); including it does not.
    Count surge pods (`maxSurge`) and HPA maximums in `springtune.budget.max-replicas`: excluded, the service
    reached 19 > 16 and the server refused connections; included (`max-replicas=4`), it stayed at 16.
  - One revert with no oscillation (bar 4): a raise that slows every session server-side is REVERTED once on R2,
    the next applies are refused `COOLDOWN`, exactly one change executed.
- **`BUDGET_EXCEEDS_SERVER` (new refusal).** Before raising a Hikari pool, apply reads the server's real limit
  (PostgreSQL `max_connections` minus `superuser_reserved_connections`; MySQL/MariaDB `@@max_connections`) and
  refuses when `springtune.budget.database-max-connections` is larger. Other databases: no check, noted in the apply
  plan. Refused with 409 `BUDGET_EXCEEDS_SERVER` (shown against a real server: configured 100 vs 20).
- **Failing database** (bar 3): with refused or timed-out connects (role `CONNECTION LIMIT`, unreachable server),
  advise does not recommend INCREASE. This needed a **product fix**: before it, a failing database got
  `ST-REC-HIKARI-001` INCREASE. New rule **`ST-REC-HIKARI-004` HOLD**: threads wait while the pool holds fewer
  connections than its maximum, or acquire timeouts occur while it does (counted with `getTotalConnections()`, so a
  connection in handoff is not mistaken for a missing one).
- **Executor ordering tests in both directions** (bar 5), end to end on a real `ThreadPoolTaskExecutor` with an
  open-loop submitter (`ExecutorApplyIntegrationTest`): a `corePoolSize` raise across the maximum writes
  `max` then `core`, its manual revert writes `core` then `max`; a raise is CONFIRMED on R6, and one that slows every
  task is REVERTED on R6 ("more tasks are rejected").
- **Apply over WebFlux security, end to end** (bar 6: the write operation is absent without Spring Security, and
  needs explicit access). `ApplyReactiveSecurityWebTest` (Reactor Netty, reactive Spring Security): no credentials
  401, wrong role 403 `ROLE_REQUIRED`, `anonymous()` + `permitAll()` 401 `NOT_AUTHENTICATED`; without Spring Security
  apply mode refuses to start (`SpringTuneAutoConfigurationTest`, unchanged).
- **Nightly load workflow** (`.github/workflows/nightly.yml`): 3 load-suite passes and 30 runs of
  `HikariApplyIntegrationTest`, no retries anywhere. The PR/push `loadtests` job runs 1 pass.

### Limiter

- Tested with **virtual threads** on Tomcat (`ServletVirtualThreadsOverloadTest`, Java 21+, needs ≥ 2 CPUs): the
  limiter caps in-handler concurrency at `max-limit` where no worker-thread ceiling exists; latency is reported,
  not asserted. Not tested: WebFlux on virtual threads, Jetty/Undertow.
- Tested with **Spring Security in front** of the application (`LimiterWithSpringSecurityTest`, HTTP Basic): only
  200/401/503, 503 also for unauthenticated requests (the limiter decides first), no leaked permit. See
  [docs/limiter.md](https://github.com/pvgiang/spring-tune/blob/main/docs/limiter.md#spring-security-in-front).

### Overhead numbers (JMH)

Pre-registered gates (brief row 14), measured on a 4 vCPU Intel Xeon @ 2.10 GHz VM, JDK 21, Boot 4.1.2; full table,
caveats and how to rerun in [docs/benchmarks.md](https://github.com/pvgiang/spring-tune/blob/main/docs/benchmarks.md):

| Gate | Measured | Verdict |
|---|---|---|
| Sampler tick with 4 components < 1 ms | 376 ± 17 µs (steady state, full 24 h windows) | pass |
| Limiter filter adds < 10 µs per request | 0.39 µs on 1 thread; 4.6 µs on 8 threads (contention, see the doc) | pass |

## Known limitations

**Apply mode** ([docs/starter.md](https://github.com/pvgiang/spring-tune/blob/main/docs/starter.md#caveats))

- **Experimental.** Bar 1 of the pre-registered bar (a design partner running advise in production) is not met;
  apply stays experimental until all six bars are.
- **Per instance.** Apply changes the instance that receives the request; behind a load balancer you cannot choose
  which one. Nothing coordinates changes across replicas; the budget cap assumes every replica could be at the same
  size.
- **Per pool.** The per-instance cap applies to each Hikari pool separately. Several pools on the same database:
  size `springtune.budget.*` for that (e.g. count each pool as a replica).
- **Ephemeral.** Applied values live only in the running process; a restart or a new pod starts from the
  configuration. The audit log is in memory too (`audit-size`, default 100) and lost on restart.
- **Surge pods and autoscaling** must be counted in `springtune.budget.max-replicas`, or the cap can be exceeded
  (reproduced in the load suite).
- **Cumulative metrics only.** SpringTune reads the first non-`StepMeterRegistry` registry; with only step
  registries (Datadog, New Relic, ...) hold-time metrics are unavailable. Registries that report deltas without
  extending `StepMeterRegistry` (OTLP delta temporality, `SimpleMeterRegistry` in `STEP` mode) give wrong results.
- A large DECREASE cannot be applied at runtime (step limit); change the configuration.
- A workload whose traffic shifts by more than 2× during verification is INCONCLUSIVE and reverted by default.
- `BUDGET_EXCEEDS_SERVER` checks PostgreSQL, MySQL and MariaDB only.
- The load suites run on Spring Boot 4.1 only; Boot 3.5 is covered by the in-JVM tests.
- **The load suite is not yet release-gating.** It gates release tags only after 20 consecutive green nightly runs
  (brief row 11); at release time the nightly has not accumulated that history yet.

**Limiter** ([docs/limiter.md](https://github.com/pvgiang/spring-tune/blob/main/docs/limiter.md#limitations))

- **Only what passes the filter is protected**: Tomcat's accept queue, `max-connections` and worker threads come
  first. Keep `max-limit` below `server.tomcat.threads.max`.
- **Runs before Spring Security**: unauthenticated requests take permits too.
- **Virtual threads**: there is no worker-thread ceiling, so the limiter is the only concurrency cap. Tested on
  Tomcat with ≥ 2 CPUs; during warm-up (`warmup-samples`) nothing is rejected, so a cold instance has no cap at all.
  Pinned to one CPU, enforce mode served almost nothing (documented, not asserted).
- **Per-instance, global limit**: no per-endpoint or per-tenant partitions.
- **Separate management port**: bypassed by port; unit-tested, not exercised end to end.
- **Servlet client disconnects** are seen only when writing the response fails; until then the request keeps its
  permit.
- **AIMD** reacts only to dropped requests; for synchronous endpoints it only grows. Use Vegas (default) or
  Gradient2.
- **Bypass rules trust request headers** (`Accept: text/event-stream`, `Upgrade: websocket`): the limiter sheds
  overload, it is not an abuse control.
- **Throughput** can drop when the limit undershoots real capacity (77–91 % of limiter-off throughput in our servlet
  load test with `min-limit` 4). Start in shadow mode.

**Release**

- The Gradle Plugin Portal and Maven Central serve the same plugin sources built by different tools (Gradle and
  Maven): same coordinates, different bytes. Only builds that pin checksums and switch repositories notice.
