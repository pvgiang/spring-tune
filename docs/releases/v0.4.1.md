SpringTune 0.4.1 hardens the GitHub Action and apply mode. Same coordinates as 0.4.0
(`io.github.winkytek.springtune`, Maven Central); no rule changes, so check results are identical to 0.4.0.

## GitHub Action

- **Verified binary.** The Action downloads the CLI jar and the release's `SHA256SUMS` and runs the jar only if its
  SHA-256 matches; a missing checksum, a missing or duplicate line, or a mismatch stops with exit code 2.
- **Input validation.** `version` must be a semantic version (blocks path traversal on the download URL).
- **Downloads.** Through the GitHub API with the workflow token, falling back to an anonymous HTTPS download; the
  token is removed from the environment before the CLI runs.
- **Pin the CLI version explicitly.** The Action at `v0.4.1` defaults to CLI **0.4.0** (the 0.4.1 jar did not exist
  when the Action was written). Set it in your workflow:

```yaml
- uses: pvgiang/spring-tune@v0.4.1
  with:
    version: "0.4.1"
```

`@v0.4.0` still defaults to the 0.1.0 CLI without checksum verification: move to `@v0.4.1`.

## Apply mode (experimental, opt-in)

- **`capacityObtained`** on every verdict, in the audit log, the `POST /actuator/tuning` response and a
  `capacity_obtained` tag on `springtune.changes`: whether the pool or executor actually reached the new size during
  verification. It never changes the verdict or triggers a revert. On real PostgreSQL, a replica whose new connection
  the server refused reports `false`.
- **The server's connection limit is re-read on every apply.** If it cannot be read, raises are refused with the new
  code **`SERVER_LIMIT_UNKNOWN`** (409); decreases are never refused. The apply plan shows when the limit was last
  checked.
- Fixed: a raise retried exactly as a cooldown ended could skip the server-limit check; an `Error` in the
  limit-reader thread refused raises until restart.
- Still experimental: 5 of the 6 pre-registered bars are met; the missing one is a team running it in production.

## Known limitations

Unchanged from [0.4.0](https://github.com/pvgiang/spring-tune/blob/main/docs/releases/v0.4.0.md#known-limitations),
plus: a server-limit read that hangs (half-open TCP, no socket timeout) refuses raises until it returns; a decrease
waits for the read.
