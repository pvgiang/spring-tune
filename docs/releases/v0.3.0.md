SpringTune 0.3.0 is the first release on Maven Central. It adds the Gradle plugin, guarded apply mode and an
adaptive concurrency limiter.

## Breaking: new coordinates

| | 0.1.0 | 0.3.0 |
|---|---|---|
| groupId | `io.github.winky.springtune` | `io.github.winkytek.springtune` |
| Java packages | `io.github.winky.springtune.*` | `io.github.winkytek.springtune.*` |
| Gradle plugin id | – | `io.github.winkytek.springtune` |

Update the groupId in your build and any custom rules (`io.github.winkytek.springtune.check.rules.Rule` in
`META-INF/services`). 0.2.0 was never released; its Gradle plugin ships in this release.

## What's new

- **Gradle plugin `io.github.winkytek.springtune`** (Gradle 8.5+, configuration cache compatible): same rules,
  reports and `springtune.yml` as the CLI and Maven plugin, with the resolved runtime classpath deciding which
  rules apply. Details: [docs/check.md#gradle-plugin](https://github.com/pvgiang/spring-tune/blob/main/docs/check.md#gradle-plugin).

- **Apply plans (advise mode, read-only).** Every INCREASE/DECREASE recommendation in `/actuator/tuning` now
  carries the property lines to commit, the connection-budget arithmetic, side effects (`minimumIdle` moves with
  a fixed-size pool, Hikari shrinks lazily) and a reminder that runtime changes are ephemeral.
- **`springtune.mode=apply` (experimental, trust level 3).** A reviewed, authenticated `POST /actuator/tuning`
  applies one current recommendation on one instance:
  - Spring Security is required (startup fails without it); anonymous callers get 401; optional `required-role`.
  - Compare-and-set on `expectedCurrent` (and optional `expectedTarget`); only the recommended value can be applied.
  - Guard: connection budget required to raise a pool, per-instance cap, max step, max growth, cooldowns, one
    change in flight, `freeze` kill switch at runtime.
  - Verification on the knob's own signals (Hikari timeouts, acquire and hold time; executor rejections) with
    automatic revert on regression or an inconclusive window. Audit log, `ApplicationEvent`, `springtune.changes`.
  - See [docs/starter.md](https://github.com/pvgiang/spring-tune/blob/main/docs/starter.md).
- **`springtune-limiter` (new, opt-in artifact).** Adaptive concurrency limit for Spring MVC and WebFlux over
  Netflix `concurrency-limits-core` 0.5.4. Off by default; shadow mode (count, never reject) until
  `springtune.limiter.enforce=true`. Health probes, actuator, management port, SSE and WebSocket are never limited.
  In the included overload test, server-side p99 dropped from ~400 ms to ~90 ms (servlet).
  See [docs/limiter.md](https://github.com/pvgiang/spring-tune/blob/main/docs/limiter.md).
- **Adoption:** issue forms (false positive, rule request, recommendation feedback, fleet/approvals/budget),
  a Grafana dashboard, and a gate-tracking page. No telemetry is collected.
- **Release:** `-Prelease` builds sources/javadoc jars and deploys to Maven Central through JReleaser.

## Known limitations

- Apply is per instance and in memory: lost on restart, not coordinated across replicas, budget cap is per pool.
- Apply security is tested end to end on servlet only; WebFlux at unit level.
- The limiter protects from the filter onward (not Tomcat's accept queue); virtual threads are untested; one
  global limit per instance.
