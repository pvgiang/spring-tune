## Runtime starter: what a first user sees

- **Per-rule evaluation status.** `GET /actuator/tuning` has a new `evaluations` list: for every rule of every pool
  and executor, `COLLECTING` (with samples and seconds seen vs needed), `NO_SIGNAL` (names the missing meter),
  `QUIET` (evaluated, nothing to recommend) or `RECOMMENDING`. An empty `recommendations[]` no longer looks like a
  broken install. The status comes from the same code path as the recommendation; a property test over 4,000
  seeded windows checks that `RECOMMENDING` appears exactly when a recommendation does, and that recommendations
  are unchanged from 0.4.1.
- **`GET /actuator/tuning/report`**: a report you can paste into a
  [recommendation feedback](https://github.com/pvgiang/spring-tune/issues/new?template=3-recommendation-feedback.yml)
  issue. It is built only from allowed fields: SpringTune's own rule IDs, numbers, enum values, setting names and
  pseudonyms (`hikari#1`, `executor#1`); pool and bean names, the audit's `who`/`why`, reasons and exception text
  are never copied. Each recommendation carries a `feedbackUrl` that pre-fills the form. Same security as the
  snapshot (read it before pasting: the guarantee covers what SpringTune copies, not what you add).
- [Design-partner page](../design-partners.md): two weeks of advise mode in staging, what you see when, how to report.

## Apply mode (experimental, opt-in)

- **A hung server-limit read no longer holds a pool connection, and a decrease no longer waits for it.** The read
  sets a network timeout on the connection it borrows (the pool's `connectionTimeout`, at most 30 s), only when the
  driver can report its timeout, so HikariCP restores it on return. Proven on PostgreSQL 16 with a TCP relay that
  stops forwarding: the connection was released about 3.0 s after the query with a 3 s bound, the pool refilled,
  and the next raise was applied.
- **Decreases are decided without reading the server limit**, in the same lock hold and from the same evaluation as
  the apply; a request that turns out to raise the pool without a fresh read is refused (`SERVER_LIMIT_UNKNOWN`).
- Still experimental: 5 of the 6 pre-registered bars are met; the missing one is a team running it in production.

## Known limitations

- **A database-side slowdown that hits a minority of connections can produce an INCREASE.** In the pre-registered
  [PetClinic benchmark](../benchmarks/petclinic.md) (S3), a lock held on one table produced `ST-REC-HIKARI-001`
  INCREASE 10→13 instead of the "don't raise" recommendation, because the mean hold time (about 140 ms) stayed under
  the 500 ms threshold while acquire time was high. Read the evidence of an INCREASE before applying it.
- A revert of a decrease raises the pool back without reading the server limit (unchanged since 0.4.0).
- With a JDBC driver that cannot report its network timeout, the limit read stays unbounded as before (the apply
  still waits at most the bound).
